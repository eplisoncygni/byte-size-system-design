Union-Find

A tiny structure that keeps a collection of groups, merges any two in one pointer change, and answers "same group?" in effectively constant time — the algorithm that heals itself as you use it.

01The problem, in plain words

You have a pile of elements and you keep being told "these two belong together." You must answer, over and over and fast: "are these two in the same group?" — while groups keep merging. As friendships form, are A and B in the same cluster? As edges are added to a graph, are these two nodes now connected? Two operations — merge two groups and test if two elements share a group — have to stay cheap with millions of elements and queries.

Analogy: island nations connected by new bridges. Each island only needs to know which capital it reports to. To check if two islands are in the same country, ask each "what's your capital?" and compare. To merge two countries when a bridge is built, you don't renumber every island — you just declare one capital now reports to the other. Everyone's allegiance is found by following the chain of command up to the top capital.

02The core idea — a forest of parent pointers

Every element points to a parent. Follow parents upward and you reach a root — an element that points to itself. The root is the group's identity. Two elements are in the same group exactly when they reach the same root.

find(x) — walk parent pointers from x up to its root, and return that root.
union(x, y) — find both roots; if they differ, point one root at the other. Merging two whole groups is a single pointer change — no member is touched.

03The catch, and the two optimizations

Naively, these trees can grow tall and stringy — a long chain — and then find degrades to an O(n) walk. Two optimizations fix that, and together they make the structure famous.

1. Union by rank / size. When merging, always attach the shorter tree under the taller one (or smaller under larger). A tree only deepens when two equal-height trees merge, so height stays logarithmic. This alone bounds find at O(log n).

2. Path compression. During find(x), after reaching the root, point every node on the path straight at the root. You flatten the path as a side effect of the query — so next time, each of those nodes is one hop away.

That self-healing is the elegant part: every query makes the structure faster for the queries that follow.

04The payoff

With both optimizations, the amortized cost per operation is O(α(n)), where α is the inverse Ackermann function. You only need one fact about α: it grows so unimaginably slowly that for any n that could physically exist — more than the atoms in the observable universe — α(n) ≤ 4. So each operation is effectively constant time, and Tarjan's proof of this bound is a celebrated result in algorithm analysis. A near-O(1) merge-and-query structure, from two one-line tweaks.

# the entire structure parent = list(range(n)) # each element starts as its own root size = [1] * n def find(x): while parent[x] != x: parent[x] = parent[parent[x]] # path halving x = parent[x] return x def union(a, b): ra, rb = find(a), find(b) if ra == rb: return if size[ra] < size[rb]: ra, rb = rb, ra # attach smaller under larger parent[rb] = ra size[ra] += size[rb]

05Key terminology

Disjoint sets (partition)
The groups never overlap; every element is in exactly one set. The structure maintains a partition of all elements. Why it matters: "exactly one set" is what makes the root a clean identity — there's never ambiguity about which group an element is in.
Representative (root)
The canonical element identifying a set — the one that points to itself. Why it matters: it's just an identity token. Which element is root is arbitrary and shifts as you union, so only ever ask "same root?", never attach meaning to the root itself.
Union by rank / size
Attach the shorter/smaller tree under the taller/larger one when merging. Why it matters: without it, trees can grow into O(n) chains. This caps height at O(log n) on its own.
Path compression
On find, repoint every node on the path directly to the root. Lighter variants — path halving, path splitting — compress less but need only one pass. Why it matters: it's what turns repeated queries cheap, and combined with union-by-rank gives the inverse-Ackermann bound.
Amortized complexity
The cost is per operation averaged over a sequence. A single find may be longish, but it flattens the path and pays forward. Why it matters: the O(α(n)) bound is an average over many operations, not a worst-case guarantee for one — the right lens for self-optimizing structures.
Inverse Ackermann α(n)
The almost-constant function in the complexity bound; ≤ 4 for all practical n. Why it matters: it's why people just say Union-Find is "effectively O(1)" in practice.

07Common confusions

It's merge-only. The basic structure can union sets but can't efficiently split one or undo a union — a one-way ratchet. Rollback/persistent variants exist at extra cost.
"Connected," not "adjacent." It answers transitive grouping (are these in the same component?), not whether there's a direct edge between two elements. It tracks equivalence classes, not the graph's links.
Compression changes shape, not membership. Flattening the trees is purely a speed optimization — the partition it represents is identical before and after.
It's for equivalence, not direction. "Same group" is symmetric. Union-Find doesn't model directed reachability (A→B but maybe not B→A).

08One-sentence summary

Union-Find keeps disjoint sets as a forest of parent-pointer trees, so merging two sets is one pointer change and testing membership is a walk to the root — and with union-by-rank plus path compression, both run in effectively constant amortized time.
