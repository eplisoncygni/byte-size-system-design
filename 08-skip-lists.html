Skip Lists

A stack of sorted linked lists where each level up is a random, sparser "express lane" — giving balanced-tree speed from coin flips instead of rotations.

01The problem, in plain words

You want a sorted collection with fast search, insert, and delete — O(log n) for all three, the guarantee a balanced binary search tree gives. The catch with balanced BSTs (AVL, red-black) is that maintaining balance is fiddly: inserts and deletes trigger rotations and recoloring, notoriously bug-prone to implement.

The skip list asks: can we get O(log n) sorted operations without any rebalancing machinery? The surprising answer is yes — using randomness instead of rotations.

Analogy: a subway system. The bottom level is the local train — it stops at every single station. The levels above are express trains that stop only at major stations, skipping the ones between. To travel far, you ride the express as far as it goes without overshooting your stop, then transfer down to the local for the last few stations. Few hops to cover a big distance, then precision at the end.

03The core idea — express lanes

Take a sorted linked list (level 0 — it holds every element). Build a sparser list above it (level 1) with only some elements, whose pointers skip over the ones between. Build a sparser one above that, and so on. Higher levels are express lanes: cover big distances in few hops, then drop down for precision.

Searching: start top-left. Repeat: move right while the next node's value is ≤ your target; when it would overshoot (or is null), drop down one level. Zig-zag right-and-down to the bottom. Each express lane skips ~half the nodes below it, so you halve the search space per level — binary search over a linked structure.

04The magic — balance from a coin flip

How do you decide which elements ride the express lanes? A balanced tree computes this and rebalances carefully. A skip list just flips a coin.

Insert the new element at level 0 always.
Flip a coin. Heads → promote it to level 1 as well.
Flip again. Heads → promote to level 2. Keep going until tails.
The streak of heads is the element's tower height.

The probabilities fall out perfectly: every element is on level 0, ~1/2 reach level 1, ~1/4 reach level 2, ~1/8 reach level 3. That's exactly the express-lane sparsity you want — each level ~half the one below — and it emerges for free from randomness: no rotations, no rebalancing pass, no bookkeeping. Expected ~log n levels, ~log n nodes touched per search.

The balance is probabilistic — not guaranteed on every operation, but overwhelmingly likely, the same spirit as a hash table's expected-case guarantee.

05Insert & delete

Insert: do a search, remembering the node where you dropped down at each level (the "update points"). Flip coins for the new tower's height. Splice the new node into each level up to that height. Delete: search, then unlink the node from every level it appears in. Both are pure local pointer surgery — nothing far from the change is touched. That locality is the reason skip lists shine in concurrent code (see below).

06Key terminology

Level 0 (base list)
The bottom linked list containing every element in sorted order. Why it matters: it's the ground truth — every element is always here; higher levels are just shortcuts into it.
Express lane (higher level)
A sparser list above, holding a random subset, with pointers that skip intervening nodes. Why it matters: skipping ~half the nodes per level is what turns O(n) walking into O(log n) searching.
Tower height (node level)
How many levels a node appears in, decided by a coin-flip streak at insertion and fixed thereafter. Why it matters: heights are random and per-node — independent of value — which is what produces the self-balancing sparsity.
Promotion probability (p)
The coin's bias. p = 1/2 is classic (~2 pointers/node); Redis uses p = 1/4 for less memory. Why it matters: it's the tunable dial trading memory (fewer levels) against speed (more nodes scanned per level).
Update points
The per-level nodes where a search dropped down — the predecessors that must be re-linked on insert/delete. Why it matters: capturing these during the search is what makes insert/delete simple local splices.
Probabilistic balance
Balance holds in expectation, not as a hard guarantee. A pathological coin run could degrade to O(n). Why it matters: it's the trade — radical simplicity for an expected (not worst-case) bound, like hashing.

07Why concurrency loves skip lists

This is the non-obvious payoff. A balanced tree's rotations can cascade and touch nodes far from the change, which makes concurrent access a locking nightmare. A skip list insert/delete is a contained, local splice — so it's dramatically easier to make lock-free or fine-grained-concurrent. That's exactly why Java ships ConcurrentSkipListMap as its concurrent ordered map: balanced trees don't parallelize cleanly, skip lists do.

08Where it's used

Lucene & othersSkip pointers over posting lists and ordered indexes to jump ahead quickly.

09Common confusions

It's randomized, not deterministic. Two skip lists holding identical data can have entirely different internal shapes depending on their coin flips.
Height is set once, at insertion. You don't re-randomize or rebalance existing nodes — new randomness only enters with new inserts.
Levels don't depend on value or position. They're independent per-node coin flips; a tiny value is as likely to be tall as a huge one.
The worst case really is O(n). The guarantee is probabilistic. If you need a hard worst-case bound (hard real-time), use a balanced tree — which also tends to have better cache behavior.

10One-sentence summary

A skip list is a stack of sorted linked lists where each higher level is a random, sparser express lane — giving expected O(log n) search, insert, and delete through simple local splices and coin-flip balancing instead of rotations, which is why it powers Redis sorted sets, LSM memtables, and concurrent ordered maps.
