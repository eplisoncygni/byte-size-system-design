LSM Trees

The write-optimized storage engine inside Cassandra, RocksDB, and LevelDB — where every write is an append, and Bloom filters, sorted files, and background merging keep reads viable.

01The problem, in plain words

You need a storage engine that can absorb an enormous volume of writes. The classic design — a B-tree — keeps rows sorted in pages on disk and updates them in place: find the page, modify it, write it back. Every write becomes a random disk I/O, the slowest pattern storage offers.

The LSM (Log-Structured Merge) tree asks: what if we never update anything in place? Every insert, update, and delete becomes an append or a new file — sequential I/O everywhere. The price is paid on the read side, and most of the design is machinery for keeping that price low.

Analogy: a busy clinic's paper records. Instead of finding each patient's folder mid-rush to scribble updates (slow, error-prone), the receptionist keeps one running notepad of today's visits, sorted by name. When the notepad fills, it's photocopied into the archive as a sealed, sorted binder — never edited again. A patient's current status = check the notepad first, then binders newest-to-oldest, stop at first mention. Periodically someone merges old binders, keeping only each patient's latest entry and discarding the dead weight. Notepad = memtable, binders = SSTables, merging = compaction.

02The write path

Append to the commit log (the WAL from Day 4) — durable, sequential, fsync'd. This is what makes the write crash-safe.
Insert into the memtable — an in-memory sorted structure (skip list or red-black tree) holding recent writes ordered by key. Write acknowledged. No disk seek ever happened.
When the memtable fills (e.g. 64 MB), flush it: stream it to disk as an SSTable — an immutable, sorted-by-key file. One sequential write.
Recycle the commit-log segment. Its job was protecting the unflushed memtable; once flushed, it's no longer needed.

Updates and deletes never touch old data. An update just writes the new version somewhere newer; the old version is shadowed. A delete writes a tombstone — a marker meaning "this key is dead." The newest entry always wins.

03The read path — where the bill is paid

A key's latest value could be in the memtable or in any SSTable. A read checks the memtable first, then SSTables newest to oldest, stopping at the first hit.

Consulting every file would be brutal — and this is exactly why every SSTable carries a Bloom filter (Day 2). "Definitely not in this file" → skip it entirely, no disk touched. "Maybe" → use the file's sparse index (the data is sorted, so an in-memory index of every Nth key plus a short scan finds the spot) to read it.

04Compaction — the merge in "merge tree"

Left alone, SSTables pile up: reads consult ever more files, and dead data (shadowed versions, tombstoned keys) wastes space. Compaction runs in the background: pick several SSTables, k-way merge them (each is already sorted — this is merge sort's merge step), keep only each key's newest version, physically discard tombstoned data, write fresh consolidated SSTables, delete the old ones.

05Key terminology

Memtable
The in-memory sorted structure (skip list / red-black tree) absorbing all incoming writes, protected by the commit log. Why it matters: it's why writes need no disk seek — and why it must be sorted: so the flush can stream out an already-sorted file.
SSTable (Sorted String Table)
An immutable on-disk file of key-value pairs sorted by key, written once at flush or compaction, never edited. Why it matters: immutability means no in-place corruption risk and sequential-only writes; sortedness enables sparse indexes and cheap merging.
Tombstone
A special record meaning "this key was deleted," written like any other entry. Why it matters: you can't erase from immutable files — deletion must be an append. Tombstones must persist long enough (Cassandra: gc_grace_seconds) or deleted data can resurrect from older files/replicas.
Flush
Streaming a full memtable to disk as a new SSTable, then recycling its commit-log segment. Why it matters: it's the moment memory becomes durable file — one big sequential write instead of thousands of random ones.
Compaction
Background merging of SSTables: newest version of each key survives, shadowed data and expired tombstones are dropped. Why it matters: it's what keeps reads and disk usage bounded. Without it the engine slowly drowns in its own files.
Write / read / space amplification
The three overheads: each logical write is rewritten several times (WAL, flush, compactions); each read may consult several files; disk holds dead data awaiting compaction. Why it matters: every LSM tuning decision trades these against each other — you can't minimize all three at once.
Sparse index
An in-memory index of every Nth key in an SSTable; sortedness lets a binary search + short scan find any key. Why it matters: full indexes for every key would be huge. Sortedness buys tiny indexes — one more payoff of keeping things sorted.

07Common confusions

It's not a tree like a B-tree is a tree. There's no single pointer-linked tree structure; "tree" refers to the leveled arrangement of files being merged. Don't picture nodes and pointers — picture sorted files stacked by age.
Deletes make data bigger before smaller. A delete is a write (the tombstone). The space comes back only at compaction — and mass-deletion workloads can drown in tombstones (a classic Cassandra incident pattern).
An update doesn't replace anything. Old versions physically remain until compaction; the engine just always finds the newest first. "Newest wins" is a read-time rule, not a write-time overwrite.
The WAL and the SSTables are different logs. The commit log is a short-lived crash-recovery journal (Day 4); SSTables are the long-lived data. Both append-only, different jobs.

08One-sentence summary

An LSM tree turns every write into an append — WAL-protected memtable, flushed to immutable sorted files — then uses Bloom filters to keep reads viable and background compaction to merge files and discard dead data, trading read and space overhead for exceptional write throughput.
